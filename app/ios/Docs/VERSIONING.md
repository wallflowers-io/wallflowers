# Pacific iOS — Versioning

Two numbers, per Apple's model:

| Key | Build setting | What it is | Format |
|-----|---------------|-----------|--------|
| `CFBundleShortVersionString` | `MARKETING_VERSION` | Public release version (what users/App Store see) | SemVer `major.minor.patch`, e.g. `0.2.0` |
| `CFBundleVersion` | `CURRENT_PROJECT_VERSION` | Build number — must **strictly increase** across every TestFlight/App Store upload | Integer, e.g. `57` |

## Single source of truth

Both live in **`ui/project.yml`** under `settings.base`. The Info.plist is **generated by xcodegen** and reads the build-setting variables:

```
CFBundleShortVersionString = $(MARKETING_VERSION)
CFBundleVersion            = $(CURRENT_PROJECT_VERSION)
```

Never hand-edit `App/Info.plist` (xcodegen overwrites it on `generate`) or the generated `WallFlowers.xcodeproj`. Change versions in `project.yml` or via the helper script, then regenerate.

## Build number = git commit count

`CURRENT_PROJECT_VERSION` tracks `git rev-list --count HEAD` — always increasing, deterministic, no manual bumps, and no "build number already used" rejections.

Caveat: cut releases from your **main / release branch** so the count only grows. Releasing from a shorter feature branch could move the number backward. (If you'd rather not depend on branch topology, swap `git_count()` in `scripts/version.sh` for a timestamp like `date -u +%Y%m%d%H%M`.)

## SemVer policy

- **major** — breaking changes / a milestone release.
- **minor** — new user-facing features, backward compatible.
- **patch** — bug fixes only.
- Stay on `0.x.y` until the DIGITAL AF Seoul launch, then cut **`1.0.0`**.

## Helper — `scripts/version.sh`

```
scripts/version.sh show                 # current marketing + build
scripts/version.sh set-build            # sync build number to git commit count, regenerate
scripts/version.sh bump patch           # 0.1.0 -> 0.1.1  (+ sync build, regenerate)
scripts/version.sh bump minor           # 0.1.0 -> 0.2.0
scripts/version.sh bump major           # 0.1.0 -> 1.0.0
```

## Release checklist

1. Merge everything for the release to your main/release branch.
2. `scripts/version.sh bump minor` (or `major`/`patch`).
3. Commit: `git commit -am "chore(release): v0.2.0"`.
4. Tag: `git tag -a v0.2.0 -m "Pacific 0.2.0"` (annotated tag = the release record).
5. `just testflight` — archives for device and uploads (see [TESTFLIGHT.md](TESTFLIGHT.md)). It re-runs `set-build` itself, so the build number is always the commit count at upload time.
6. In App Store Connect → TestFlight, answer the export-compliance question on the new build (manual per build until export docs land — see the EXPORT COMPLIANCE note in `project.yml`).
7. `git push --follow-tags`.

Each `bump` prints the exact commit + tag commands to run.

Because the build number is the commit count, uploading twice from the same commit is rejected as a duplicate `CFBundleVersion` — commit something (step 3) before re-uploading.
